# Database

Move37 Operational System runs on **Postgres 15 via Supabase**, with **Row Level Security enabled on every table** (no exceptions — a table without RLS is a bug, not a shortcut) and an **append-only migration history** (existing files are never edited; corrections land as new migrations). See [`RULES.md` §2 — Database & Migrations](RULES.md#2-database--migrations) and [§3 — Row Level Security](RULES.md#3-row-level-security-rls) for the non-negotiable rules; this document is the descriptive map of what those rules produced.

This file is generated by reading `supabase/migrations/*.sql` and `src/lib/supabase/types.ts` directly — it does not restate `RULES.md` policy, and every fact below was checked against the SQL rather than assumed. Where a widely-repeated figure (elsewhere in the repo's own docs) turned out to be wrong against the SQL, this file uses the verified number and flags the discrepancy inline.

## Migration workflow

| Aspect | Convention |
|---|---|
| Filename | `YYYYMMDDHHMMSS_slug.sql` (e.g. `20260814140000_drop_legacy_user_ai_keys.sql`) |
| Count (2026-09-15) | 39 files in `supabase/migrations/` |
| Baseline | `20260101000000_production_baseline.sql` — a squashed snapshot of all schema history up to that date. It defines **80 tables** and **49 enums** via `CREATE TABLE IF NOT EXISTS` / `CREATE TYPE`, all idempotent guards. (An earlier audit figure of "97 tables" was incorrect and has been corrected across the docs as of 2026-09-15.) |
| Editing rule | Never edit an applied migration. If a past migration was wrong, write a new one that corrects it (`RULES.md` §2.1). |
| Idempotency | Baseline and most later migrations use `IF NOT EXISTS` / `IF EXISTS` guards and end with `NOTIFY pgrst, 'reload schema';` to hot-reload PostgREST's schema cache. |
| Apply locally | `npm run db:reset` (wraps `supabase db reset`, replays every migration against the local Postgres container) |
| Apply to a running branch | `npx supabase migration up` (applies only unapplied migrations — used for hotfix-style migrations, e.g. `20260614120000_task_meta_sop_playbook_invoices.sql` per its own header comment) |
| Types regen | `npx supabase gen types typescript --project-id <ref> > src/lib/supabase/types.ts`, or hand-edit the Row/Insert/Update interface (`RULES.md` §2.4) |

**Current live table count:** 80 (baseline) − 11 dropped + 16 added by later migrations = **85 tables**, all with RLS enabled at creation time (verified: 80 + 16 = 96 `ENABLE ROW LEVEL SECURITY` statements across the whole migration history; 11 of those tables were later dropped, leaving 85/85 live tables with RLS). See [Enum catalog](#enum-catalog) and [Domains](#domains) for what changed.

**`types.ts` is currently stale.** It is missing 5 live tables that exist in the SQL and are read by application code: `idea_location_legislation`, `idea_market_opportunity`, `idea_risk_and_validation` (from `20260619000002_idea_new_steps.sql`, used in `src/app/ideas-refiner/actions.ts`) and `mkt_seo_keyword`, `mkt_seo_rank_history` (from `20260622000000_mkt_seo_keyword.sql`, used in `src/app/marketing/[ideaId]/traffic/seo-actions.ts`). Regenerate before relying on these tables' generated types.

**CONCURRENTLY note:** every `CREATE INDEX` in this repo's migrations runs as a plain (non-`CONCURRENTLY`) statement inside the migration's implicit transaction — `supabase db reset`/`migration up` wraps each file in a transaction, and `CREATE INDEX CONCURRENTLY` cannot run inside one. This is fine for small/empty tables (all current index migrations are). For a **large, live production table**, run the equivalent `CREATE INDEX CONCURRENTLY` by hand outside a transaction, in a maintenance window, instead of adding it to a migration file — `20260627000000_mkt_funnel_indexes.sql` documents this exact caveat inline.

## Naming conventions (as observed)

Tables are **`snake_case`, mostly singular**, but the convention is mixed in practice — read a table's own name, don't assume:

| Pattern | Examples |
|---|---|
| Singular core entities | `project`, `idea`, `profiles` *(plural — exception)*, `agency`, `feedback`, `prompt`, `sop` |
| `project_*` | `project_task`, `project_file`, `project_link`, `project_video`, `project_work_feedback`, `project_agreement_version` |
| `internal_*` | `internal_project`, `internal_goal`, `internal_key_result`, `internal_project_task`, `internal_project_work_feedback` |
| `idea_*` | `idea_icp`, `idea_prd`, `idea_database`, `idea_styles`, `idea_market_opportunity`, `idea_playbook_version` |
| `mkt_*` | `mkt_prospect`, `mkt_campaign`, `mkt_landing`, `mkt_signal`, `mkt_seo_keyword` |
| `conversation_*` | `conversation_project_external_message`, `conversation_private_message_thread`, plus one `_emoji` reaction table per message/thread table |
| Plural exceptions | `profiles` (not `profile`) |

Column conventions:

| Column | Meaning |
|---|---|
| `created_by uuid` | Row owner; RLS "creator" tier and server-action inserts key on this (`RULES.md` §5.2) |
| `created_at` / `updated_at timestamptz` | Set via `DEFAULT now()`; `updated_at` maintained by the `set_updated_at()` trigger |
| `authorized_users uuid[]` | Membership array checked via `auth.uid() = ANY(authorized_users)` — on `project`, `sop`, `sop_version`, `project_agreement_version`, plus `project.external_conversation_authorized_users` / `internal_conversation_authorized_users` for per-thread visibility |
| `viewed_by uuid[]` | Per-message read-receipt tracking on every `conversation_*_message`/`_thread` table |

Index naming is **inconsistent by design history** — both `idx_<table>_<col>` (older) and `<table>_<col>_idx` (newer) styles are live simultaneously, and in five cases the *same* column has both, i.e. a genuine duplicate index (see [Known gaps](#known-gaps-audit-2026-09-15)). Do not assume one style is authoritative; check `\d <table>` before adding a new index.

Policy naming follows `"table: tier verb"` (e.g. `"task: developer insert"`, `"idea: creator all"`, `"user_ai_settings: own row"`) — see [Row Level Security](#row-level-security).

| `public.is_admin_or_manager()` | boolean | `type IN ('admin','manager')` |
| `public.is_staff_role()` | boolean | `type IN ('admin','manager','operational')` |
| `public.is_operational_user()` | boolean | `type IN ('developer','client','qa')` — project-member tier; name is historical |

`public.rls_auto_enable()` is an **event trigger** (fires on `CREATE TABLE`/`CREATE TABLE AS`/`SELECT INTO` in the `public` schema) that automatically runs `ALTER TABLE … ENABLE ROW LEVEL SECURITY` on every new table — a safety net so a forgotten `ENABLE ROW LEVEL SECURITY` statement in a new migration doesn't ship an RLS-less table. It logs success/failure via `RAISE LOG` rather than failing the migration.

The **standard three-tier model** (admin/manager: all; creator: own rows; project member: read via `authorized_users`) is defined once in [`RULES.md` §3.2](RULES.md#3-row-level-security-rls) — apply it verbatim for new tables unless the feature needs a different shape (like `project_task`, below).

The **`project_task` per-role matrix** (`RULES.md` §3.4): admin/manager unrestricted; `developer` full CRUD on any task type in an authorized project; `client` restricted to `type = 'client_requests'` (insert/update need project membership, delete needs `created_by = auth.uid()`); `qa` the same shape for `type = 'qa_requests'`. Every INSERT policy across the schema requires `created_by = auth.uid()` in `WITH CHECK`.

`public.profiles_guard_type_change()` (from `20260628000000_security_profiles_type_guard.sql`) is a `BEFORE UPDATE` trigger on `profiles` that blocks any authenticated, non-admin/manager user from changing their own `type` — closing a privilege-escalation hole where the baseline's `"profiles: update own"` policy had a `USING` clause but no `WITH CHECK`, so an UPDATE could silently self-promote to `admin`. The same migration added an explicit `WITH CHECK (id = auth.uid())` to that policy as defense-in-depth.

**Verified facts:** 85/85 currently-live public tables have RLS enabled (see [Migration workflow](#migration-workflow) for how this was counted; an earlier "97/97" figure was incorrect and has been corrected repo-wide). Every `SECURITY DEFINER` function in the schema pins `search_path` as of `20260628000000`.
